## Verified source-faction usability deficiency and correction

Code review found that navigation labelled source factions but still offered an opposite-faction-only source to a character whose faction was known. This could make a Horde player follow the Alliance Drakefire itinerary or a source accessible only to Alliance, despite a useful faction label. It was a source-selection issue, not an equipment-eligibility correction.

The existing shared navigation now uses the client faction when UnitFactionGroup reliably reports Alliance/Horde. It selects compatible explicit quest/vendor source restrictions in both compact choices and the detailed navigation section. Unknown/unsupported/erroring faction APIs retain qualified alternatives instead of guessing. No API is assumed to exist. Reliable active-quest evidence can override a stale published restriction, including an accepted matching-faction stage within a published itinerary;an active Both-faction shared stage alone cannot establish the opposite final reward path. Historical completion alone does not override current source-faction selection.

Final reward-side metadata controls branch selection, while Both-faction intermediate quests retain their own published sides. This preserves the four Both-faction Horde itinerary skull tasks without incorrectly enabling that final Horde reward path for an Alliance character solely through a shared active stage. Source filtering does not mutate gear faction/class/equip/stat/armour/BoE eligibility or settings. Source levels and uncertain current availability remain visible planning requirements, not assumed character progress.
